# オーバーフロー (Overflow)

数値の階乗は非常に急速に大きくなります。\
例えば、20の階乗は 2,432,902,008,176,640,000 です。これはすでに32ビット整数の最大値である 2,147,483,647 よりも大きくなっています。

算術演算の結果が特定の整数型の最大値よりも大きくなる場合、それを**整数オーバーフロー (integer overflow)** と呼びます。

整数オーバーフローが問題になるのは、算術演算の契約（前提条件）に違反するからです。\
特定の型の2つの整数間の算術演算の結果は、同じ型の別の整数になるはずです。
しかし、*数学的に正しい結果*がその整数型に収まらないのです！

> 結果が特定の整数型の最小値よりも小さくなる場合、その事象を**整数アンダーフロー (integer underflow)** と呼びます。\
> 簡潔にするため、このセクションの残りの部分では整数オーバーフローについてのみ説明しますが、ここで述べることはすべて整数アンダーフローにも当てはまることに留意してください。
>
> [「変数」セクション](02_variables.md)で書いた `speed` 関数は、いくつかの入力の組み合わせでアンダーフローを起こしていました。
> 例えば、`end` が `start` よりも小さい場合、結果は負になるはずですが `u32` は負の数を表現できないため、`end - start` は `u32` 型でアンダーフローを起こします。

## 自動的な型昇格は行われない

考えられるアプローチの1つは、結果をより大きな整数型に自動的に昇格（プロモート）させることです。
例えば、2つの `u8` 整数を足して結果が 256 (`u8::MAX + 1`) になった場合、Rustはその結果を、256を保持するのに十分な大きさを持つ次の整数型である `u16` として解釈するという選択もあり得たでしょう。

しかし、これまで説明してきたように、Rustは型変換に関して非常に厳格です。自動的な整数の型昇格は、整数オーバーフロー問題に対するRustの解決策ではありません。

## 代替案

自動昇格を除外したとすると、整数オーバーフローが発生したときに何ができるでしょうか？\
突き詰めると、2つの異なるアプローチに行き着きます：

- 演算を拒否する
- 期待される整数型に収まる「妥当な」結果をひねり出す

### 演算を拒否する

これは最も保守的なアプローチです。整数オーバーフローが発生したときにプログラムを停止します。\
これは、[「パニック」セクション](04_panics.md)ですでに見た仕組みであるパニックを通じて行われます。

### 「妥当な」結果をひねり出す

算術演算の結果が特定の整数型の最大値よりも大きい場合、**ラップアラウンド (wrap around / 折り返し)** することを選択できます。\
特定の整数型のとり得るすべての値を円のように考えると、ラップアラウンドとは、最大値に達したときに最小値から再び始まることを意味します。

例えば、1 と 255 (=`u8::MAX`) の間で**ラッピング加算 (wrapping addition)** を行うと、結果は 0 (=`u8::MIN`) になります。
符号付き整数を扱っている場合も同じ原則が適用されます。例えば、ラッピングありで 127 (=`i8::MAX`) に 1 を足すと、-128 (=`i8::MIN`) になります。

## `overflow-checks`

Rustでは、整数オーバーフローが発生したときにどちらのアプローチを使用するか、開発者自身が選択できるようになっています。
この振る舞いは、プロファイル設定の `overflow-checks` によって制御されます。

`overflow-checks` が `true` に設定されている場合、整数演算がオーバーフローするとRustは**実行時にパニック**します。
`overflow-checks` が `false` に設定されている場合、整数演算がオーバーフローするとRustは**ラップアラウンド**します。

ところで、プロファイル設定とは何でしょうか？それについて見ていきましょう！

## プロファイル (Profiles)

[**プロファイル**](https://doc.rust-lang.org/cargo/reference/profiles.html)とは、Rustコードのコンパイル方法をカスタマイズするために使用できる設定オプションの集まりです。

Cargoには、`dev`、`release`、`test`、`bench` の4つの組み込みプロファイルが用意されています。\
`dev` プロファイルは、`cargo build`、`cargo run`、または `cargo test` を実行するたびに使用されます。これはローカル開発向けであり、コンパイル時間の短縮と優れたデバッグ体験を優先するために、実行時のパフォーマンスを犠牲にしています。\
一方、`release` プロファイルは実行時のパフォーマンスに最適化されていますが、コンパイル時間が長くなります。これを使用するには、`--release` フラグ（例：`cargo build --release` や `cargo run --release`）を使って明示的に要求する必要があります。
残りの2つのプロファイルはこれらをベースにしています。`test`（`cargo test` で使用）は `dev` の設定を継承し、`bench`（`cargo bench` で使用）は `release` の設定を継承します。実際には、ほとんどの時間を `dev` で過ごし、パフォーマンスが重要になるときにいつでも `release` に切り替えることになります。

> 「プロジェクトをリリースモードでビルドしましたか？」というのは、Rustコミュニティではほぼミーム（定番ネタ）になっています。\
> これは、Rustに不慣れな開発者が、プロジェクトをリリースモードでビルドしていないことに気づく前に、ソーシャルメディア（RedditやTwitterなど）でRustのパフォーマンスについて不満を言う現象を指しています。

また、カスタムプロファイルを定義したり、組み込みのプロファイルをカスタマイズしたりすることもできます。

### `overflow-checks` のデフォルト値

デフォルトでは、`overflow-checks` は次のように設定されています：

- `dev` プロファイルでは `true`
- `release` プロファイルでは `false`

これは2つのプロファイルの目的に沿ったものです。\
`dev` はローカル開発向けであるため、潜在的な問題をできるだけ早い段階で浮き彫りにするためにパニックを起こします。\
一方、`release` は実行時のパフォーマンスに合わせて調整されています。オーバーフローのチェックはプログラムを遅くするため、ラップアラウンドを優先します。

しかし同時に、2つのプロファイルで異なる振る舞いをすることは、微妙で気づきにくいバグにつながる可能性があります。\
私たちの推奨は、両方のプロファイルで `overflow-checks` を有効にすることです。黙って誤った結果を生成するよりは、クラッシュする方がましだからです。実行時のパフォーマンスへの影響はほとんどのケースで無視できる程度です。パフォーマンスが極めて重要なアプリケーションに取り組んでいる場合は、ベンチマークを実行して許容できるかどうかを判断できます。
